Verified on the live stack
Scheduled runs: all fired on time and succeeded.
CoinGecko ran at 14:35, 14:40 and 14:45 UTC, with 50 values each time.
Twelve Data forex ran at 14:45.
Twelve Data stocks and ETFs ran at 14:45, while US markets were open.

How it works
Jobs live in backend/seed.toml under [[jobs]]. Each has a schedule, either every N minutes on the clock or daily at a UTC time, plus optional filters and an optional one-time retry. Jobs removed from the file are disabled.
Nine default jobs, of which seven are active. Stocks and ETFs every 15 minutes during New York trading hours, forex every 15 minutes, crypto every 5 minutes, crypto dominance every 2 hours, and daily candles, ECB rates and indicators once a day. The two FRED jobs are disabled until you settle FRED's terms and add a key.
No overlapping runs: a database lock per job stops two runs of the same job from overlapping, even across processes.
Execution history: every run is recorded with its trigger, status, record count and error. Each job also shows its last outcome and next run time. python -m app.cli jobs lists this, and python -m app.cli run JOB runs a job now.
Isolation: a failing job or provider doesn't affect the others, and runs interrupted by a restart are closed as failed on the next start.
Limitations
Exchange holidays aren't modelled: a market-hours job still polls on a holiday. That costs credits but stays within budget.
Direct collection bypasses jobs: collect commands run outside any job, so they skip the job lock and the execution history. They do use the provider rate limits.
One scheduler only: run a single backend with the scheduler on. Two would each spend the provider budget.
Rate-limit counts reset on restart: they're held in memory. The budget check keeps planned usage in bounds, and an HTTP 429 from a provider pauses requests until its allowance resets.
Decision for you
To trigger jobs through the API, set ADMIN_API_KEY in .env. .env.example now shows how to generate one. Without it, API triggers stay disabled and the command line still works.

What it does
Data-quality checks: a new job runs every 15 minutes, reads only the database, and records each problem as an issue:

Issue	Detected when
stale	A series has nothing newer than its job allows
gap	Two consecutive values are too far apart
conflict	A provider re-sends a stored value with a different number
spike	A price moves more than 20 %, or a rate or yield more than 1 point
discrepancy	Two providers disagree on the same instrument at the same time
Thresholds are set per job in seed.toml, and markets that close at weekends are handled. Rates that are only recorded when they change (the ECB key rates) are skipped.

Suspect values: conflicts and spikes mark the observation suspect. That is the only change ever made to a stored row; values are never corrected.

Backfill: each provider gets a daily job that re-fetches a few open gaps from the provider's history, counted in its budget (Twelve Data is now at 711 of 800 a day). It closes each gap as filled, no_data (a holiday, for example) or unrecoverable. Binance prices land in the last group, because Binance keeps no price history.

Where to see it: a new Data Quality dashboard, a read-only GET /api/v1/quality/issues endpoint, and panels on Collector Monitoring for collection latency and run duration.

Compression and retention: compression is on, after 30 days by default (COMPRESS_AFTER_DAYS). It has already compressed 56 of 61 chunks live, though the saving is small at the current data volume. Retention is available through two settings and off by default.

Restart and outage: both are tested and documented in the README's "Restart and Recovery" section. Restarting the live backend closed one interrupted run as failed and every job resumed on schedule.

Two flaws the live data exposed, both fixed
False gaps: the first live check reported 5,824 gaps. They came from history imported at CoinGecko's hourly granularity, being compared with 5-minute polling. Gaps are now checked only in data collected since the job existed, with at most 20 per series. The live check then found none.
Comparison too narrow: the provider comparison rarely compared anything, because the ECB's fixing is dated midnight of its reference day. It now compares the older of the two latest values with the other provider's value at that time. EUR/USD rows will appear after today's ECB fixing, which is collected at 16:00 UTC.
